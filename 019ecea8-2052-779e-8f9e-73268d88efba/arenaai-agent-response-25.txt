### Why Safari probably failed to render the fonts initially

You confirmed earlier that downloading `http://192.168.0.127:8765/assets/fonts/ChironSungHK.ttf` returned a 24.5 MB file. That means Safari CAN reach the font, but isn't using it. Two likely causes, both unrelated to subsetting:

1. **MIME type**: Python's built-in `http.server` returns `Content-Type: application/octet-stream` for `.ttf`. Safari (stricter than Chrome) **silently refuses to use it as a font** with that MIME. Fix: use the new `serve.py` instead:
   ```bash
   cd web
   python serve.py
   ```
   It registers `font/ttf` correctly. Refresh Safari — fonts should appear.

2. **Slow first paint over LAN**: 24.5 MB × 4 fonts = ~100 MB to download before the page can render text. If Safari times out the font load, it falls back to system fonts. The optional WOFF2 conversion brings each font down to ~10-12 MB and load time drops dramatically without touching glyph coverage:
   ```bash
   cd web/scripts
   pip install fonttools brotli
   python convert-fonts-to-woff2.py
   ```
   Re-run any time you replace the masters. Future-proof against new glyphs in remote pages.

## Summary of fixes

### 1. `awk: Invalid multibyte data detected` warnings
ImageMagick on Windows ships with Chinese-localised error messages (`無法開啟...`). When piped into `awk`'s `length()` under Git Bash's non-UTF-8 default locale, awk threw the multibyte warning. **Fix:** wrap awk with `LC_ALL=C` and switch to byte-oriented processing so awk never tries to interpret bytes as UTF-8 characters.

### 2. Custom fonts now inline → "Vincent" reads clearly
Added two transformations to the inliner:

| Step | What | Why it's necessary |
|------|------|-------------------|
| **Recursive font inlining** | `@font-face src: url('https://.../lato-regular.ttf')` is fetched and rewritten as `data:font/ttf;base64,...`. Same for Parisienne, Cubic 11, Compact. | resvg-js (and any sandboxed renderer) can't perform network I/O, so without inlining it falls back to a default font and stacks every glyph at the same x-coordinate (which is what you saw as "letters piling up"). |
| **Nested-SVG unwrap** | After embedding the icon-SVG into the splash as `<image href="data:image/svg+xml;...">`, the inliner detects this pattern and **unwraps** it into a real inline `<svg viewBox=...>…inner content…</svg>` block in the outer document. | resvg-js doesn't resolve `@font-face` declarations from inside a referenced `<image>` element — but it **does** resolve them from nested `<svg>` elements. Without unwrapping, the icon's Lato/Parisienne text inside the splash would still pile up even though the fonts were technically present in the document. |
| Cycle safety | Recursion depth-cap of 4 prevents infinite loops on self-referencing SVGs. | — |

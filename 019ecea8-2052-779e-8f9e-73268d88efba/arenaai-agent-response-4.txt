## Summary

### Root causes

1. **`@resvg/resvg-js` never installed** — my script tried `npm init -y` inside a directory called `.resvg-helper`, but **npm refuses directory names that start with a dot** ("Invalid name"). Result: the install command silently no-op'd, and the Node fallback was never available.
2. **Android-12 SVGs reference a remote image** (`<image href="https://...appiconmastersvg.svg">`) — no rasteriser will fetch a remote `<image>` for security reasons.
3. **Even after inlining** that remote reference as a base-64 `data:` URI, ImageMagick's `-draw` engine still can't parse data URIs (it tries to open them as filenames).
4. **No SVG files were left behind for inspection** because the original script used `mktemp -d` + `trap` cleanup.
5. **Failure messages spewed the entire base-64 data URI** (thousands of lines) into the terminal.

### Fixes (v1.0.3, verified in this sandbox: 7/7 PNGs generated)

| # | Fix |
|---|-----|
| 1 | Renamed `.resvg-helper` → **`_resvg_helper`** (no leading dot) and **wrote `package.json` manually** instead of calling `npm init -y`. The Node fallback now bootstraps correctly. |
| 2 | New **`inline_remote_images()`** Node helper auto-fetches every `<image href="https://...">` and rewrites it as `data:image/svg+xml;base64,...` inside the SVG before rasterisation. Works for nested SVGs, PNGs, etc. |
| 3 | When inlining has happened **and** no Inkscape/rsvg is present, the script **skips ImageMagick entirely** and goes straight to the Node WASM fallback (ImageMagick will never succeed with embedded data URIs). |

| 6 | **`.gitignore`** added entries for `_resvg_helper/`, `_inline_remote.js`, and `svg/` (regeneratable artefacts). |

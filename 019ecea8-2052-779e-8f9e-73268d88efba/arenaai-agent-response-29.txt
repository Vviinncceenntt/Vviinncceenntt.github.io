The issue: the `style.css` **also** references `thepeakfontplus-regular.ttf` with a relative URL, which means it tries to fetch `https://vviinncceenntt.github.io/thepeakfontplus-regular.ttf`. Let me check if that exists:

**Font is 15.7 MB.** That's the problem. WebView's font-loading timeout is hitting before the 15.7 MB TTF finishes downloading over a slow connection — and `font-display: block` means the WebView paints with the system fallback after the 3-second timeout.

Look at the source `style.css` again:
```css
@font-face {
  font-family: 'The Peak Font Plus', '隨峰體Plus', 'ThePeakFontPlus', ...;
  src: url('thepeakfontplus-regular.ttf') format('ttf');
  font-display: block;
}
```

`format('ttf')` is **invalid** — the spec requires `format('truetype')`. Browsers ignore the rule when format is unknown! That's a bug on your source page. Let me verify:

So there are **two** problems on your source page (I'll mention both but the app needs to be resilient regardless):
1. `format('ttf')` should be `format('truetype')` (or omit the `format` hint).
2. `font-family: 'The Peak Font Plus', '隨峰體Plus', ...` on `@font-face` is wrong — `font-family` in `@font-face` must be a single name. Multiple aliases need separate `@font-face` rules.

Both of these are easily fixable on GitHub. But the app should also degrade gracefully. The best way to guarantee the font on RN is to **inject an additional `@font-face`** via WebView (lightweight, just a CSS string referencing the SAME remote URL — no base64 needed, just a corrected rule).
